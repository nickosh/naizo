# Publishing `nakajs`

The first interactive npm publication creates the package. Later releases use npm Trusted Publishing (OIDC) from `.github/workflows/release.yml`; no `NPM_TOKEN` secret is needed. npm requires the package to exist before adding a trusted publisher. See [npm's publishing instructions](https://docs.npmjs.com/creating-and-publishing-unscoped-public-packages/) and [trusted publisher requirements](https://docs.npmjs.com/cli/v11/commands/npm-trust/).

## First version: `0.1.0`

1. Create an [npm account](https://www.npmjs.com/signup), verify its email address, and enable two-factor authentication. Use Node.js 24 and npm 11 locally. Make the workflow changes available on GitHub's `main`, then work from the same clean checkout that will receive the version tag. These commands publish the real library; no placeholder package or separate website creation step is needed.

   ```sh
   git switch main
   git pull --ff-only
   git status --short
   node --version
   npm --version
   npm login --registry=https://registry.npmjs.org
   npm whoami --registry=https://registry.npmjs.org
   npm view nakajs name version --registry=https://registry.npmjs.org
   ```

   The status output should be empty. `npm view` returning `E404` means there is no public package under this name; other errors need investigation. If it returns someone else's package, choose an available name or a scoped name and update package metadata, release guards, and CDN links first. Do not proceed under another maintainer's package name.

2. Verify `package.json` is at `0.1.0`, install the locked dependencies with pnpm 9.15.9, and build. Using `pnpm exec` ensures the repository's Vite+ tools run.

   ```sh
   node -p "JSON.parse(require('node:fs').readFileSync('package.json', 'utf8')).version"
   npm exec --yes --package=pnpm@9.15.9 -- pnpm install --frozen-lockfile
   pnpm exec vp check
   pnpm exec vp test
   pnpm exec vp pack
   node --check dist/naka.js
   node --check dist/naka.min.js
   git diff --exit-code dist/naka.js
   ```

3. Pack once, inspect the manifest, and publish that exact tarball. Keep these commands in the same terminal so `RELEASE_DIR` stays available. The manifest guard requires exactly `LICENSE`, `README.md`, `package.json`, and the four distribution files.

   ```sh
   RELEASE_DIR=$(mktemp -d)
   npm pack --ignore-scripts --json --pack-destination "$RELEASE_DIR" > "$RELEASE_DIR/pack.json"
   node scripts/release.ts package "$RELEASE_DIR/pack.json"
   cat "$RELEASE_DIR/pack.json"
   npm publish "$RELEASE_DIR/nakajs-0.1.0.tgz" --access public --ignore-scripts --registry=https://registry.npmjs.org
   npm view nakajs@0.1.0 version dist.integrity --registry=https://registry.npmjs.org
   ```

   Complete the interactive 2FA prompt. This creates `nakajs@0.1.0`. A version cannot be overwritten. Keep the local first publication free of `--provenance`: npm provenance is generated by supported CI providers, and cannot be added retroactively to this local publication. Later OIDC publications from this public repository include provenance.

4. Tag the same clean commit and send the tag to GitHub:

   ```sh
   git tag -a v0.1.0 -m "Release v0.1.0"
   git push origin v0.1.0
   ```

   In GitHub → **Actions → Release → Run workflow**, select **`v0.1.0`** in the workflow ref selector, enter tag **`v0.1.0`**, and **uncheck `publish_npm`**. This verifies the tagged source and creates the GitHub Release with `naka.js`, `naka.min.js`, and the npm tarball attached. There is no second npm publication in this bootstrap run. With GitHub CLI, the equivalent is `gh workflow run release.yml --ref v0.1.0 -f tag=v0.1.0 -F publish_npm=false`. The release created with `GITHUB_TOKEN` does not start a second release workflow automatically. Configure GitHub Pages separately in repository **Settings → Pages → Source → GitHub Actions** if the playground is wanted.

## Configure token-free publishing

When the next version is ready, open npm → **Packages → nakajs → Settings → Trusted publishing**, choose **GitHub Actions**, and enter:

| Setting              | Value                                                       |
| -------------------- | ----------------------------------------------------------- |
| Organization or user | `nickosh`                                                   |
| Repository           | `nakajs`                                                    |
| Workflow filename    | `release.yml`                                               |
| Environment          | Leave blank; the publishing job does not use an environment |
| Allowed action       | Enable direct `npm publish`                                 |

Enter only the filename, not `.github/workflows/release.yml`. Newly configured publishers must complete a successful OIDC publication within **two days** or expire; create the configuration when a new version is ready to publish, or recreate an expired configuration. Skipping an already published identical version does not validate the OIDC connection. See [npm's configuration and expiry rules](https://docs.npmjs.com/trusted-publishers/).

After the first successful OIDC publication, set npm **Publishing access → Require two-factor authentication and disallow tokens**. Trusted publishing continues to work with this setting. Remove any obsolete npm publish tokens or GitHub `NPM_TOKEN` secret; this workflow does not use them.

## Subsequent stable releases

Update `package.json` locally (for example, `npm version minor --no-git-tag-version`), build and verify, and commit the reviewed change through the normal repository workflow. Once that version's commit is on `main`, create and push its annotated `vMAJOR.MINOR.PATCH` tag. The workflow no longer bumps versions, commits, or creates tags itself; this supersedes the original one-click bump inputs.

Use either entry point:

- Run **Actions → Release** from the version tag (select it in the workflow ref selector) with the same tag input and `publish_npm` checked. This publishes to npm and then creates or updates the GitHub Release.
- Publish a GitHub Release in the UI against an existing tag. The `release: published` event verifies, publishes to npm, and attaches the assets. If npm fails, the UI-created release already exists; rerun the failed workflow after correcting configuration.

The workflow accepts stable versions only, requires the tag's commit to belong to `main`, requires the workflow run's commit to equal that tag for accurate provenance, and requires the tag to match `package.json`. It installs locked dependencies without a release cache, runs checks/tests/build, audits the npm file manifest, and transfers the resulting tarball by artifact ID to a separate OIDC job. That job installs no project dependencies and publishes with lifecycle scripts disabled. Only the final GitHub Release job has repository write permission.

Retries skip npm publication only when the registry's existing version has the same SHA-512 integrity as the built tarball. A registry/network failure or differing package fails the run. Never move a version tag to repair a published package; use a new version for changed content. The manually published `0.1.0` is bootstrapped with npm publishing disabled because local and CI toolchain differences can produce different tarball bytes.

For an authentication failure, check the exact owner/repository/workflow fields, publisher expiry, direct-publish permission, and that the job runs on a GitHub-hosted runner. The workflow uses Node 24 and npm 11, exceeding npm's OIDC minimums of Node 22.14.0 and npm 11.5.1. `npm whoami` checks interactive credentials and is not an OIDC test. [npm troubleshooting](https://docs.npmjs.com/trusted-publishers/)

The action references are pinned to reviewed commit IDs and kept current by weekly Dependabot updates. CI and Pages use Node 24 and pnpm 9.15.9; their dependency caches remain separate from uncached release builds. Publication outcomes belong to npm and GitHub Releases/tags, not project memory documents.
