# Publishing `nakajs`

The first interactive npm publication creates the package. Later releases use npm Trusted Publishing (OIDC) from `.github/workflows/release.yml`; no `NPM_TOKEN` secret is needed. npm requires the package to exist before adding a trusted publisher. See [npm's publishing instructions](https://docs.npmjs.com/creating-and-publishing-unscoped-public-packages/) and [trusted publisher requirements](https://docs.npmjs.com/cli/v11/commands/npm-trust/).

## First version: `0.1.0`

The commands below use **fish shell** syntax. Run them from the repository root, in order, and continue only after each command succeeds (except the expected `E404` package-name check described below).

1. Create an [npm account](https://www.npmjs.com/signup), verify its email address, and enable two-factor authentication. Install the [global Vite+ CLI](https://viteplus.dev/guide/global-cli) with environment management enabled. VP reads Node 24.22.0 from `.node-version` and pnpm 12.14.0 from `package.json#packageManager`; the pinned Node includes npm 11. Use VP for local installation, checks, builds, and scripts, and native npm for registry login, package manifests, and publication. Make the workflow changes available on GitHub's `main`, then work from the same clean checkout that will receive the version tag. These commands publish the real library; no placeholder package or separate website creation step is needed.

   ```fish
   git switch main
   git pull --ff-only
   git status --short
   vp env install
   vp env current
   vp node --version
   npm --version
   npm login --registry=https://registry.npmjs.org
   npm whoami --registry=https://registry.npmjs.org
   npm view nakajs name version --registry=https://registry.npmjs.org
   ```

   The status output should be empty. `npm view` returning `E404` means the public registry lookup found no package; it does **not** guarantee npm will allow registering the name. npm also checks name similarity during publication. If publication rejects the name, stop and follow [Package-name rejection](#package-name-rejection). Other errors need investigation. If the lookup returns someone else's package, choose an available name or a scoped name and update package metadata, release guards, and CDN links first. Do not proceed under another maintainer's package name.

2. Verify `package.json` is at `0.1.0`, install the locked dependencies through VP, and build. The global CLI delegates development commands to the project's exact Vite+ 1.3.0 toolchain.

   ```fish
   vp node -p "JSON.parse(require('node:fs').readFileSync('package.json', 'utf8')).version"
   vp install --frozen-lockfile
   vp check
   vp pack
   vp test
   vp env exec -- npm ci --prefix .github/release-tools --ignore-scripts --no-audit --no-fund
   vp node --test .github/release-tools/test.cjs
   vp node --check dist/naka.js
   vp node --check dist/naka.min.js
   git diff --exit-code dist/naka.js
   ```

   For this manual first-version bootstrap, the rebuilt readable bundle must match the commit that will be tagged. If the freshness check reports a change, review and commit the generated bundle before continuing. Subsequent Release Please releases update it automatically.

3. Pack once, inspect the manifest, and publish that exact tarball. Fish uses `set RELEASE_DIR (mktemp -d)` to create a temporary directory and store its path. Keep these commands in the same fish session so `RELEASE_DIR` stays available; it does not need to be exported. The manifest guard requires exactly eight public files: `CHANGELOG.md`, `LICENSE`, `README.md`, `package.json`, and the four distribution files. Private release tooling is excluded.

   ```fish
   set RELEASE_DIR (mktemp -d)
   npm pack --ignore-scripts --json --pack-destination "$RELEASE_DIR" > "$RELEASE_DIR/pack.json"
   vp node scripts/release.ts package "$RELEASE_DIR/pack.json"
   cat "$RELEASE_DIR/pack.json"
   npm publish "$RELEASE_DIR/nakajs-0.1.0.tgz" --access public --ignore-scripts --registry=https://registry.npmjs.org
   npm view nakajs@0.1.0 version dist.integrity --registry=https://registry.npmjs.org
   ```

   Complete the interactive 2FA prompt. A successful publication creates `nakajs@0.1.0`; authentication alone does not mean publication succeeded. Continue to tagging only after the publish command succeeds and the registry confirms the expected version and integrity. A version cannot be overwritten. Keep the local first publication free of `--provenance`: npm provenance is generated by supported CI providers, and cannot be added retroactively to this local publication. Later OIDC publications from this public repository include provenance.

4. Tag the same clean commit and send the tag to GitHub:

   ```fish
   git tag -a v0.1.0 -m "Release v0.1.0"
   git push origin v0.1.0
   ```

   In GitHub → **Actions → Release → Run workflow**, select **`v0.1.0`** in the workflow ref selector, enter tag **`v0.1.0`**, and **uncheck `publish_npm`**. This verifies the tagged source and creates the GitHub Release with `naka.js`, `naka.min.js`, and the npm tarball attached. There is no second npm publication in this bootstrap run. With GitHub CLI, the equivalent is `gh workflow run release.yml --ref v0.1.0 -f tag=v0.1.0 -F publish_npm=false`. The release created with `GITHUB_TOKEN` does not start a second release workflow automatically. Configure GitHub Pages separately in repository **Settings → Pages → Source → GitHub Actions** if the playground is wanted.

## Package-name rejection

An `E403` containing `Package name too similar to existing package kafkajs` is npm's name-policy rejection, even when the earlier lookup returned `E404` and browser authentication completed. Changing tokens, clearing the npm cache, changing the version, or moving publication into CI does not address this rejection. npm's [name guidelines](https://docs.npmjs.com/package-name-guidelines/) also apply to unused unscoped names.

Keep the intended name `nakajs` (`D36`) and request a review through [npm Support](https://www.npmjs.com/support), signing in to the npm account used for publication. Explain that this is a new-name similarity review; approval is npm's decision. This is a suggested message:

```text
Subject: Request to review package-name similarity rejection for nakajs

I am trying to publish the first version (0.1.0) of my package, nakajs.
Repository: https://github.com/nickosh/nakajs

naka.js is a zero-dependency browser library for persisting state inside
HTML files and rendering declarative lists. It is an independent project
with a different purpose from kafkajs.

The public registry lookup for nakajs returned E404. After completing
browser authentication, npm publish failed with E403:
"Package name too similar to existing package kafkajs"

Could you review the automated similarity rejection and advise whether
the unscoped name nakajs can be approved for this project?

Command: npm publish nakajs-0.1.0.tgz --access public --ignore-scripts --registry=https://registry.npmjs.org
Environment: Node 24.22.0, npm 11.19.1
```

Include the relevant error text rather than the entire debug log, which can contain authentication URLs or identifiers. Wait for npm's response before retrying this rejected name. Keep `0.1.0` when retrying if that version remains absent from the registry. Once npm permits publication, repeat the bootstrap checks and packing steps from the clean commit that will be tagged; changes made while waiting require a new tarball. Confirm publication before creating the tag or running the GitHub bootstrap. If npm declines the name, select a replacement explicitly and update package metadata, release guards, and CDN links together before packing again.

## Configure token-free publishing

When the next version is ready, open npm → **Packages → nakajs → Settings → Trusted publishing**, choose **GitHub Actions**, and enter:

| Setting              | Value                                                       |
| -------------------- | ----------------------------------------------------------- |
| Organization or user | `nickosh`                                                   |
| Repository           | `nakajs`                                                    |
| Workflow filename    | `release.yml`                                               |
| Environment          | Leave blank; the publishing job does not use an environment |
| Allowed action       | Enable direct `npm publish`                                 |

Enter only the filename, not `.github/workflows/release.yml`. Newly configured publishers must complete a successful OIDC publication within **two days** or expire; create the configuration when a new version is ready to publish, or recreate an expired configuration. Skipping an already published identical version does not validate the OIDC connection. See [npm's configuration and expiry rules](https://docs.npmjs.com/trusted-publishers/).

After the first successful OIDC publication, set npm **Publishing access → Require two-factor authentication and disallow tokens**. Trusted publishing continues to work with this setting. Remove any obsolete npm publish tokens or GitHub `NPM_TOKEN` secret; this workflow does not use them.

## Enable explicit release preparation

Before activation, enable repository **Settings → Actions → General → Workflow permissions → Allow GitHub Actions to create and approve pull requests**. Preparation uses only the built-in `GITHUB_TOKEN`; no PAT, GitHub App, or stored npm token is required. GitHub does not start new workflow runs for events caused by `GITHUB_TOKEN` (except `workflow_dispatch`/`repository_dispatch`), so the bot-created release PR receives **no CI run**. Its verification is the read-only bundle job in the **Prepare release** run that wrote it; confirm that run succeeded before merging, and do not mark CI checks as required for this PR. For the same reason, preparation explicitly dispatches the publisher with `workflow_dispatch`. See [GitHub's trigger rules](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).

Complete both parts of the manual `v0.1.0` bootstrap above before requesting another release. The manifest starts at `0.1.0`; the adapter checks for the public GitHub release and npm package before calling Release Please. Configure the npm trusted publisher for **`release.yml`**, not `prepare-release.yml`, when the next version is ready.

## Subsequent stable releases

Ordinary pushes check for a merged release PR but **do not create or refresh one**. Request preparation explicitly from **Actions → Prepare release → Run workflow**, select **main**, and leave `release_tag` blank. Equivalent fish command:

```fish
gh workflow run prepare-release.yml --ref main
```

Preparation first checks for releasable changes and records the exact source commit. A separate job with read-only repository permission installs locked dependencies, builds all outputs with `vp pack`, and tests the freshly built bundle. It transfers only `dist/naka.js` by artifact ID to the PR job. Release Please 17.11.2 opens or refreshes one release PR updating `package.json`, `.release-please-manifest.json`, `CHANGELOG.md`, and the readable `dist/naka.js` bundle. The minified bundle, ESM, and declarations remain untracked and are rebuilt for npm publication. Conventional Commits since the previous release determine the version: before `1.0.0`, `fix:` bumps patch, while `feat:` and breaking changes bump minor. Requests with no releasable changes succeed without a PR. Review the proposed version, changelog, readable bundle, and the successful preparation run, then merge the release PR. Its merge starts verification and publication automatically.

For an explicit stable version, put a `Release-As:` footer in a Conventional Commit. For example, run this after staging the intended changes, then deliver the commit through the normal reviewed contributor workflow:

```fish
git commit -m "chore: prepare the stable API release" -m "Finalize the reviewed public API and release notes for the stable package." -m "Release-As: 1.0.0"
```

When this commit enters `main`, the preparation workflow reads every commit newly introduced by that push. Any `Release-As:` footer line requests preparation; malformed values, prereleases, and build metadata are rejected. Release Please still decides whether the footer changes the proposed version, so use it in a Conventional Commit. Use a version greater than the previous release. A footer already present before the push does not retrigger preparation. If you squash a contributor PR, keep the footer in the resulting commit message.

Ordinary source changes do not require a manually committed bundle. CI builds before testing; the preparation bundle job builds and tests the readable bundle written into the release PR, and tagged publication checks its freshness again.

An existing release PR stays unchanged on later ordinary pushes. Run **Prepare release** again with the blank input to explicitly refresh it before merging if later changes should be included. Explicit refreshes also update the bundle when release notes are unchanged. Preparation verifies the planned source against the current primary branch before and after PR writes. If it reports that the branch advanced during the build or update, request preparation again and verify the refreshed PR before merging; a failed preparation is not ready to merge. Keep its version and changelog aligned with the intended source: the release tag points to the merged release PR commit, including preceding changes on `main`.

On merge, Release Please immediately creates a plain `vMAJOR.MINOR.PATCH` tag and a **draft** GitHub release. Preparation resolves the tag's exact commit, checks its source and release metadata, and dispatches **`release.yml` at that tag** with `expected_sha`. The merge/recovery check has repository/PR/label/workflow permissions; the PR job has repository/PR/label writes. Project dependency installation and build/test execution happen in a separate job with read-only repository permission and no write token. Preparation jobs have no npm identity. Only the isolated npm publish job has `id-token: write`.

The publisher requires a stable tag belonging to `main`, equality between the tag and workflow commit, equality to the supplied expected SHA, and the matching package version. It installs locked dependencies without a release cache, runs checks/tests/build, audits the eight-file npm manifest, and transfers one verified tarball by artifact ID. The OIDC job installs no project dependencies, verifies the tarball hash and bundle bytes, and publishes with lifecycle scripts disabled. After npm succeeds, the asset job attaches `naka.js`, `naka.min.js`, and the tarball, then publishes the draft while preserving Release Please's notes.

## Recovery and manual tagged releases

An unfinished stable draft blocks new preparation. Correct the failed configuration or service issue, then recover its existing tag from **Prepare release** using `release_tag`, for example:

```fish
gh workflow run prepare-release.yml --ref main -f release_tag=v0.2.0
```

Recovery validates the existing tag, GitHub release, exact commit, and membership in `main`, then dispatches publication at that tag with the expected SHA. This handles failures after draft/tag creation, after npm publication, or during asset attachment. Preparation recovery always enables npm publishing; for an interrupted local `v0.1.0` bootstrap, rerun **Release** at that tag with `publish_npm=false` instead. A failed handoff before the draft exists can be retried by rerunning the preparation workflow; once the draft exists, use recovery.

Retries skip npm publication only when the registry's existing version has the same SHA-512 integrity as the verified tarball. Matching GitHub assets are reused and missing assets are uploaded. Differing package integrity or asset bytes fail; assets are never overwritten. Registry/network errors fail rather than being treated as an absent version. Never move a version tag to repair a published package; changed content needs a new version. Inspect unexpected assets before deciding how to resolve a conflict.

The existing manual entry points remain available. A manually prepared tag must already contain the rebuilt readable bundle; rebuild and commit it before tagging. The Release Please PR automates that commit for the normal release path:

- Run **Actions → Release** from the version tag, with the same `tag`, `publish_npm` checked, and optionally the full `expected_sha` for additional source validation. For example: `gh workflow run release.yml --ref v0.2.0 -f tag=v0.2.0 -f expected_sha=FULL_COMMIT_SHA -F publish_npm=true`.
- Publish a GitHub Release in the UI against an existing stable tag. The `release: published` event verifies, publishes to npm, and attaches assets. If npm fails, this manually published GitHub release already exists; rerun the failed workflow after correcting configuration.
- For the local first-publish bootstrap only, use `v0.1.0` with `publish_npm=false` as described above. The workflow confirms that npm already has `nakajs@0.1.0` and rejects this bypass for other tags. Local and CI toolchain differences can produce different tarball bytes.

Remote settings, interactive bootstrap, and a live automated release are owner rollout steps. Local tooling tests validate logic with fixtures and the pinned updater; they do not validate GitHub permissions or npm OIDC credentials.

For an authentication failure, check the exact owner/repository/workflow fields, publisher expiry, direct-publish permission, and that the job runs on a GitHub-hosted runner. The workflow uses Node 24.22.0 and its bundled npm 11 (logged in the publish job), exceeding npm's OIDC minimums of Node 22.14.0 and npm 11.5.1. `npm whoami` checks interactive credentials and is not an OIDC test. [npm troubleshooting](https://docs.npmjs.com/trusted-publishers/)

The action references are pinned to reviewed commit IDs and kept current by weekly Dependabot updates. CI and release builds use `setup-vp`, which reads the Vite+ version from `package.json`, Node from `.node-version`, and pnpm from `packageManager`. `pnpm-workspace.yaml` delegates environment management to VP and records resolution policy in the lockfile; pnpm 12.14.0 is required to interpret this configuration consistently. CI caches package-manager data; release builds disable that cache. Release tooling tests run in CI only; release jobs verify the artifact rather than re-testing the tooling. GitHub Pages deploys from `ci.yml` only after verification passes on `main`, using the bundles CI just built and tested; `release.yml` contains no Pages job, so its npm publishing job remains the workflow's only OIDC identity. The publishing job reads `.node-version` with `setup-node`, installs no project dependencies, and uses the npm 11 bundled with that Node for OIDC. Publication outcomes belong to npm and GitHub Releases/tags, not project memory documents.

## CDN URLs and automatic updates

Publishing to npm makes the verified distribution available through jsDelivr and unpkg. Use one provider in each HTML file:

```html
<!-- jsDelivr -->
<script src="https://cdn.jsdelivr.net/npm/nakajs@latest/dist/naka.js" defer></script>
```

```html
<!-- Alternative: unpkg -->
<script src="https://unpkg.com/nakajs@latest/dist/naka.js" defer></script>
```

Replace `dist/naka.js` with `dist/naka.min.js` for the prebuilt minified bundle. These explicit browser-bundle paths work with a classic deferred script tag.

The `@latest` URLs follow new npm releases as CDN caches refresh. Availability and cache invalidation are not instantaneous; pages pick up an updated script on a later reload after cache refresh. For a fixed artifact, use an exact package version, for example `https://cdn.jsdelivr.net/npm/nakajs@0.1.0/dist/naka.js` or `https://unpkg.com/nakajs@0.1.0/dist/naka.js`. See the providers' [npm URL and caching documentation](https://github.com/jsdelivr/jsdelivr#npm) and [unpkg documentation](https://unpkg.com/).

Npm publication is the CDN deployment step; no CDN upload or additional generated-file commit during publication is needed. A source change or CI build alone does not change what these npm-backed URLs serve. The package/version must exist on npm; local examples can keep using their relative `dist/naka.js` paths for development or offline use.

The repository tracks the readable bundle from release preparation (`D35`); between releases it can lag current source. Run `vp pack` before local tests or the demo. Source changes need no bundle commit: the Release Please PR updates it automatically from a verified preparation build, and tagged publication checks its freshness. Release builds regenerate all four outputs and publish the verified tarball without committing generated files back to Git.

## Maintain release tooling locally

Use VP-managed Node for the private tooling package and install its separate npm lockfile with lifecycle scripts disabled:

```fish
vp env exec -- npm ci --prefix .github/release-tools --ignore-scripts --no-audit --no-fund
vp node --test .github/release-tools/test.cjs
```

The exact Release Please dependency and its lockfile live in `.github/release-tools/`; they are not runtime dependencies or npm distribution files. Root dependencies remain managed by pnpm through VP. Review dependency changes together with the real-updater regression tests.
