### Fourth review — recommended priorities and acceptance corrections (2026-10-18)

Recommendations only; accepted milestones above and below are unchanged. The goal is a trustworthy small persistence runtime before more templates, website work, or generalized synchronization features.

1. **M3.1 + minimal CI first:** generate the consumer artifact from source, verify its freshness immediately, and test the real package entrypoints (`EC30`, `EC37`). A passing build alone does not establish that consumers import the same API as the declarations. Preserve IIFE startup when specifying package `sideEffects`; do not blindly mark every entry side-effect free.
2. **Then proposed M4.0, ahead of examples/site work:** retain regression tests for the confirmed failures and define a small runtime contract. Test the built artifact in isolated documents, with controllable storage/permission/write delays, before replacing the core. Moving the playground folder may accompany M3.1 but should not gate data-integrity work.
3. **M4.1 must establish complete state and safe boundaries:** install the entire chosen database before hydration/events (`EC32`); validate JSON shape before touching DOM/cache (`EC04`, `EC33`); restrict API values to JSON and define getter ownership (`EC35`); attach bindings before asynchronous handle discovery (`EC34`). Hydration is observational: no timestamps, type coercions, dropped keys, or automatic recovery writes. Missing initial data and malformed data require different paths. Prefer explicit `bind(root)` initially over a global MutationObserver, and define reset, composition, and external-update behavior for an actively edited field.
4. **M4.2 needs an explicit durability contract:** separate in-memory, browser-cached, and on-disk revisions; add an awaitable save/flush result and visible pending/error/conflict states (`EC36`). Serialize immutable payloads, acknowledge only completed writes, and retain recoverable last-good data. Store merge-base and browser-revision checkpoints consistently; do not introduce unrelated asynchronous writes to separate stores without a crash-recovery rule. Hidden/pagehide flushing improves recovery but cannot guarantee that asynchronous disk work finishes before the page exits.
5. **Implement serialization against adversarial fixtures:** apply the `D13` Unicode-escape correction (`EC08`); locate exactly one real database script in the permitted document location, distinguishing comments, templates, other script text, wrong types, and duplicate IDs. Preserve BOM/encoding and unrelated bytes, or explicitly define/reject unsupported source encodings. The existing “first matching block” prose is insufficient for this acceptance criterion.
6. **Scope concurrency honestly:** read-before-write and browser locks reduce races, but cannot atomically compare and replace a file against a CLI/editor that does not participate in the same protocol. Record the supported single-writer/cooperation boundary, retain backups, and test the remaining read/write window. Stronger guarantees need cooperation from both writers. Body/template changes on disk also need a reload policy; JSON hydration alone cannot apply them to an already-open view.

Recommendation for the existing proposals:

| Proposal                  | Fourth-review recommendation                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `D18` namespace/schema    | Add a format version and reject unsupported versions now. Namespace flattening is optional and should not block the safety rewrite; retain the existing buckets for the first hardening slice. If adopted before the consumer skill, specify collisions (`fields.x` versus `custom.x`) and preserve an original copy during migration.                                                                       |
| `D19` item identity       | Useful before item-level merge and targeted item APIs. Specify uniqueness, missing IDs, duplicates, copy/fork behavior, and numeric-ID/index ambiguity. Do not silently overwrite application-owned `id` values or mutate documents merely by opening them.                                                                                                                                                  |
| `D20` three-way merge     | Retain a base for recovery, but first ship explicit, recoverable conflicts. Stage automatic non-overlapping merges later; arrays remain atomic until delete-versus-edit and concurrent ordering rules are tested. A focus/blur delay alone is not an editing-conflict policy.                                                                                                                                |
| `D21` targeted capture    | Adopt in preference to debounced whole-document scanning; update the store immediately and debounce persistence only. Include duplicate bindings and late binding tests.                                                                                                                                                                                                                                     |
| `D22` text handling       | Adopt plain text by default. Defer built-in rich text and a custom sanitizer; a sanitizer is a separate security surface, not a prerequisite for safe persistence.                                                                                                                                                                                                                                           |
| `D23` attribute baking    | Adopt export-clone-only baking. Preserve native form defaults and keep ordinary reads/exports from changing live editing state.                                                                                                                                                                                                                                                                              |
| `D24` write safety        | Adopt the queue, exact-payload snapshot, unlink, and file checks, plus the durability contract above. `_meta.id` is a useful document identity but copied files share it; distinguish linking an existing source from saving a new copy and treat identity as a heuristic, not proof of physical-file identity.                                                                                              |
| `D25` modularity/adapters | Adopt small internal modules, side-effect-free ESM, an isolated instance with readiness/disposal, and injectable I/O for tests. Defer a public universal adapter API, arbitrary-root/multi-document support, and a local server until a concrete consumer needs them. Keep snapshot export separate: fetching `location.href` can return transformed server HTML, and is not proof of original local source. |

Before calling M4 complete, exercise fresh-document reloads of all namespaces, invalid-source recovery, edits during startup and in-flight saves, failed/blocked storage, exact saved revisions, script-safe JSON, source preservation, and repeat initialization/teardown. Browser checks must cover actual input/reset/composition behavior, two tabs, and at least a real permission/save/reopen smoke test; mocked handles cannot validate native permissions or OS-level concurrency.

The browser support statement also needs qualification: picker use depends on secure context, user activation, and same-origin-with-top-level rules, rather than “top-level tabs only” ([File System Access specification](https://wicg.github.io/file-system-access/)). Chrome can offer persistent permission, so “a permission prompt per session” is not universal ([Chrome permission documentation](https://developer.chrome.com/blog/persistent-permissions-for-the-file-system-access-api)). Downloads are copies, not write-back to the agent’s existing file. Lifecycle guidance cannot promise completion of asynchronous saves on termination ([Chrome lifecycle documentation](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)).

### Simplification follow-up — small runtime and few authoring requirements (2026-10-18)

`D26` records the owner’s product priority. The following implementation choices are recommendations, not accepted amendments. Prefer this narrower scope when evaluating the earlier review suggestions; do not require every proposed abstraction before starting M4.

| Area                              | Recommended simplification                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Mutation path                     | One store and one internal change path shared by events, API calls, and list actions. Eliminate full-document capture from ordinary edits and parsing from getters. Serialize once per persistence batch where possible; bake only the export clone. A timer, a current write promise, and a pending revision should be evaluated before adding a general scheduler or state-machine framework.                                                                                                                         |
| Public data API (`D18`)           | The low-ceremony priority increases the value of a single namespace and common `get`/`set`/`delete` methods. Decide D18 before adding another family of namespace-specific methods; retain convenient list actions. A one-time, explicit migration may be worthwhile now, with collision detection and source preservation. This refines the fourth review’s preference to keep all buckets during hardening; no format change is yet accepted. Avoid dotted paths, expressions, proxies, and a general patch language. |
| List identity (`D19`)             | Keep IDs optional for ordinary repeaters. The accepted row-to-object mapping in D15 can preserve items through local moves without compulsory persistent IDs. Application-provided IDs pass through. Add identity requirements only for a feature that actually needs cross-version item matching; do not reserve or generate business IDs on every boot.                                                                                                                                                               |
| Conflicts/storage (`D20`)         | Keep D16’s disk fingerprint plus visible, recoverable conflict backup for the first safe version. Without automatic merging, a separate IndexedDB merge-base database is unnecessary; this narrows the earlier recommendation to retain a full merge base immediately. Keep IndexedDB for remembered file handles. Preserve an unresolved backup until resolution instead of silently replacing it with each conflict; defer merge engines and history databases. Existing concurrent-writer risks remain open.         |
| Binding/validation (`D21`, `D22`) | Delegate events, hydrate on boot and explicit `bind(root)`, and preserve inferred templates. No unconditional document-wide observer, application schema declarations, mandatory item IDs, or validation of business fields. Check JSON compatibility and structures actually consumed by bindings; unknown data passes through. Plain-text bindings avoid a built-in rich-text sanitizer.                                                                                                                              |
| Structure/integration (`D25`)     | Use a few internal modules as useful for testing, with one ordinary document instance by default. Keep test seams private; defer a public adapter/plugin system, arbitrary-root multi-instance API, local server, and fetching remote HTML as a source substitute. Keep both short/data attributes and the cheap API alias.                                                                                                                                                                                             |
| UI and workflow                   | Retain the small status pill, useful list controls, download fallback, and recovery actions. Normal edits/save should be automatic; reserve interruption for actual invalid source, destructive file mismatch, or unresolved conflict. Defer configuration dashboards, merge editors, and general undo history. Keep basic accessibility and print fixes.                                                                                                                                                               |
| Performance and verification      | Report minified+gzip bundle size and work per edit before setting a hard size ceiling. Retain data-preservation regression tests and focused browser smoke tests; test infrastructure does not add runtime dependencies. Avoid incremental JSON serializers, virtualization, or workers until measurements justify them.                                                                                                                                                                                                |

Inspection/probe evidence: in the current freshly built source IIFE, one input event on 500 standalone fields caused one JSON parse, two serializations, and 500 attribute writes; one custom setter caused two parses, three serializations, and 500 attribute writes; 100 custom getters caused 100 parses. These are operation counts from isolated jsdom, not browser latency measurements. Current unminified gzip sizes were 6,314 bytes for root `naka.js` and 5,985 bytes for the generated IIFE; they are not minified size targets or rewrite estimates.

Keep the practical sequence: generated artifact/minimal CI → focused regression harness → store/targeted binding → safe queued persistence → useful binding polish and examples. No extra platform layer is required to follow that sequence. Decide the public data shape early to avoid implementing both the expanded bucket API and D18.

## M4 — Core runtime re-architecture & hardening (`D12`–`D17`, `EC02`, `EC06`–`EC17`)

Sequence is binding: `M4.1` and `M4.2` replace the DOM-as-truth capture loop and the full-document disk write. Items in `M4.3` are implemented only against the store so no hardening is done twice.

- [ ] **M4.1 — In-memory store, merge semantics, and single-attribute key contract (`D15`, `D12`; `EC06`, `EC11`, `EC14`, `EC15`, `EC16`)**:
  - Build one in-memory `NakaDatabase` in `initNaka()` from the resolved source; route `Naka.get` / `set` / `getList` / `getField` / `setField` / `updateItem` / `deleteField` through it; serialize to `#nakadb` text, `localStorage`, and disk only on save.
  - Merge DOM reads into `store.fields` and per-item source objects (`WeakMap` from rendered `[naka-item]` to its object); never reset `fields` / `lists`; pass unknown fields, lists, and item keys through untouched; key removal is explicit.
  - Bind exclusively via `naka` / `data-naka` / `data-naka-field` inside and outside items; remove the `id`, `name`, and `field_${idx}` fallbacks; leave unannotated inputs untracked.
  - Bump `_meta.updatedAt` only when serialized `fields` / `lists` / `custom` changed; never on hydration or boot.
  - Debounce capture (about 150 ms) and flush synchronously on `pagehide` / `visibilitychange: hidden`; split `readElementValue()` from `bakeElementAttributes()` so baking runs only in hydration and export (`D14`).
  - Preserve stored `<select>` values with no matching `<option>` and warn instead of coercing to `""`.
  - Keep `naka-ignore` / `data-naka-ignore` strictly as a binding exclusion; mark injected runtime UI with `data-naka-runtime` (`D12`, `EC07`).
- [ ] **M4.2 — Surgical disk sync, conflict handling, and storage keys (`D16`, `D13`; `EC02`, `EC08`, `EC10`, `EC13`, `EC17`)**:
  - `writeToDisk()` reads the file via `fileHandle.getFile()`, replaces only the first `<script id="nakadb">` block (insert after `<head>` when absent), and writes the otherwise byte-identical text; escape `</script` and `<!--` in the serialized JSON (`EC08`).
  - Treat read-before-write and the window `focus` / `visibilitychange` check as the external-change detector (`EC10`); hydrate from disk when the on-disk block differs from the snapshot hash.
  - Store a synchronous string hash of the canonical JSON in `nakadb_disk_hash_<key>`; normalize `/index.html` → `/` and support optional `naka-id` / `data-naka-id` / `_meta.id` scoping in `getPageKey()` / `getSnapshotKey()`.
  - On three-way divergence keep the discarded browser state under `nakadb_backup_<key>` and surface a conflict notice with a restore action in the status pill (`EC17`); add an unlink action that clears the persisted handle; evaluate `showOpenFilePicker` as the link gesture to avoid the overwrite prompt.
  - Keep full `Naka.exportHTML()` serialization (with `data-naka-runtime` and auto-template stripping) for the Blob-download fallback and call `URL.revokeObjectURL()` after download (`EC02`, `EC13`).
- [ ] **M4.3 — Element bindings, list repeater support, and symmetrical API on top of the store (`D14`, `D15`; `EC09`, `EC12`, `EC13`)**:
  - Numeric coercion (`number | null`) for `input[type="number"|"range"]`, boolean `open` for `<details>`, `<select multiple>`, `contenteditable` variants (`""`, `"true"`, `"plaintext-only"` vs `"false"`), and non-leaf element guards.
  - Auto-template lifecycle: mark inferred templates with `data-naka-auto-template`, regenerate from the first `[naka-item]` on boot, scope the template selector to a direct child `template[naka-template]`, and strip on export only when the list has $\ge 1$ item (`EC09`).
  - Self-bound `[naka-item]` roots, per-row radio `name` scoping, valid control placement for `<table>` / `<tbody naka-list>` / `<tr naka-item>`, attribute-escaped list names in injected controls, and a documented guard or rejection for nested lists.
  - Finalize `window.Naka` / `window.NakaDB`: `getField`, `setField`, `updateItem`, `deleteField`, `unlink`, plus a `naka:change` event; update `AGENTS.md`, `README.md`, and `docs/PRODUCT.md` contracts (body is template, JSON is data) in the same change.
- [ ] **M4.4 — Automated verification and edge-case closure (`EC02`, `EC06`–`EC17`)**:
  - Vitest `jsdom`: store merge and pass-through, key contract, change-only `updatedAt`, debounce and flush, select preservation, escaping, block replacement on sample file text, hash snapshot, and conflict backup.
  - Browser-level suite (Playwright or Vitest browser mode) with a mocked `showSaveFilePicker` / `showOpenFilePicker` and an in-memory `FileSystemFileHandle`: handle persistence across reloads, surgical write leaving unrelated bytes untouched, read-before-write detection, conflict notice and restore, unlink, and Blob fallback. `jsdom` cannot exercise these paths.
  - Promote every verified case to `fix` in `docs/EDGE_CASES.md`; keep anything not covered explicitly `OPEN` or `PARTIAL`.
