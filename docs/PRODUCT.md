# naizo — Product Definition

Status: `v0.1.0` specification adopted 2026-10-18, updated 2026-11-13 (`D38`–`D51`). Companions: [PLAN.md](PLAN.md) (what to build and sequencing), [DECISIONS.md](DECISIONS.md) (why major decisions were made), [EDGE_CASES.md](EDGE_CASES.md) (boundary behaviors and resolution status), [USAGE.md](USAGE.md) (comprehensive usage and authoring reference).

## One-liner

**`naizo.js`** (`naizo`, npm package `naizojs`) is a zero-dependency, lightweight script (~15.7 KB minified + gzipped, ~23.2 KB gzipped unminified) providing a self-persisting HTML built-in database (`#naizodb`) and declarative list repeater (`[naizo-list]` / `[data-naizo-list]`) that keeps human edits in the browser and AI agent edits on disk in two-way sync.

## Name & Meaning

In Japanese, **_naizō_ (ないぞう)** unites two homophonous concepts that describe how `naizo.js` works:

- **内蔵 (_naizō_ — built-in / embedded / housed within):** Every HTML file houses its own built-in JSON micro-database (`<script id="naizodb" type="application/json">`) directly inside `<head>`.
- **内臓 (_naizō_ — internal organs / viscera):** Plain HTML markup is a static skeleton; `naizo.js` provides the vital internal organs—reactive inputs, dynamic list repeaters, and two-way disk synchronization—that make the file a living, self-persisting application.

The `naizo.js` brand mark and `#dot` Status Pill indicator—**three rounded squares arranged in an upward pyramid enclosed within a circular ring** ([docs/design/status-pill-reference.html](design/status-pill-reference.html), [docs/design/status-pill-states.png](design/status-pill-states.png))—translates the architecture and philosophy of `naizo.js` directly into geometry and motion:

1. **Core Architectural Metaphor (`丸` + `三つ石`):**

Everything needed to run the application lives inside this circle—portable, sandboxed, and free of external runtime dependencies.
   - **The Three Inner Stones (`三つ石` / `内蔵` — Built-in Application Engine):** Three `22×22` rounded squares (`rx="4.5"`, `4u` gutter, centered at `(50, 50)`) represent the three internal pillars working together inside the document: **reactive UI (`View`)**, **application logic (`Logic`)**, and **embedded `#naizodb` state (`State`)**—as well as the foundational web trinity (`HTML + CSS + JS`).
2. **Cultural, Typographic & Heraldic Meanings:**
   - **内蔵 / 内臓 (_Naizō_ — Built-In & Internal Organs):** The outer ring acts as a protective vessel or body, while the three inner stones represent the living internal organs tucked cleanly inside.
   - **Kanji 「品」 (_Hin / Shina_):** Arranging one square over two squares directly forms the kanji **品**, evoking three qualities of software craftsmanship: **品質 (_Hinshitsu_ — Quality & precision)**, **作品 (_Sakuhin_ — every single-file HTML app as a complete, finished work/artifact)**, and **品格 (_Hinkaku_ — dignity, restraint, and zero bloat)**.
   - **Kamon Heritage — 丸に三つ石 (_Maru ni Mitsuishi_ — Three Stones in a Circle):** In Japanese heraldry (_Kamon_), _Maru ni Mitsuboshi_ (丸に三つ星) symbolizes Orion's belt and Mōri Motonari's _Lesson of the Three Arrows_ (three elements bound together are unbreakable). Its square counterpart, **丸に三つ石 (_Maru ni Mitsuishi_)**, grounds that triad into three interlocking foundation stones (_ishigaki_), enclosed in a **丸 (_Maru_)** signifying completeness, harmony (**和** — _wa_), and protection.
3. **Visual Psychology & Design Guardrails:**
   - **Dynamic Stability & Rule of Three:** Placing a bottom-heavy pyramid of rounded squares inside a circle balances portability (outer circle) with grounded stability (inner foundation stones). In Gestalt perception, two shapes read as a binary toggle and four as a grid; three shapes in a triangle are the minimum count that reads instantaneously as a **complete, interconnected system** (`1 root node → 2 child nodes`) without pareidolia.

Tight corner rounding (`rx="4.5"` = `~20.5%` of `22u` stone width) gives a tactile "polished stone" feel at `62px` hero scale while preserving crisp, flat parallel edges at `16px–20px` favicon and Status Pill sizes.

## Problem

A single `.html` file can be almost any application: a custom dashboard, an inventory studio, a personal tracker, an interactive option lab, a visual canvas, an engineering notebook, or a living specification generated in seconds with an AI coding agent (Antigravity, Claude Code, Gemini CLI, Cursor, Codex). Yet plain HTML has two persistent limits when humans interact with it:

1. **Static HTML forgets user input:** Editing fields, toggling items, or adjusting controls in a local `.html` file disappears on page refresh.
2. **Browser storage hides edits from AI agents:** Persisting state only to `localStorage` traps changes inside the browser profile. When a CLI or IDE AI agent reads the `.html` file from disk on the next turn, it cannot see the human's edits.

`naizo.js` bridges both worlds with a single `<script>` tag: human edits in the browser sync into `<script id="naizodb" type="application/json">` and back to the `.html` file on disk, while external agent edits to `#naizodb` on disk automatically hydrate the DOM on reload or live watch.

## Target users

- **Primary:** Humans and AI coding agents collaborating through local, self-saving single-file HTML applications of any kind (custom micro-tools, dashboards, option/design labs, studios, notebooks, plans, specs, and checklists).
- **Secondary:** Authors of standalone, local-first single-file HTML applications who want persistent state and repeating list controls without a backend server or runtime dependencies, and creators sharing interactive single-file HTML apps on static web hosts (such as GitHub Pages) that visitors can customize and save to their own PC (`D41`).

## Global picture: connected lifecycles (`D40`, `D41`, `D43`)

A `naizo.js` HTML file is a self-contained application that moves seamlessly between **local disk**, **the web**, and **external HTTP APIs/webhooks**:

1. **Local Mode (`file://`, `localhost`, or linked disk file) — Human ↔ AI Agent Co-Editing (`D16`, `D40`):**
   - The human opens `plan.html` locally in the browser and links the file on disk (via the bottom-right pill or `⌘S` / `Ctrl+S`).
   - Edits in the browser immediately cache in `localStorage` and surgically rewrite only `<script id="naizodb">` on disk (and flush automatically when switching away from the tab).
   - When a CLI or IDE AI agent edits `#naizodb` on disk, `naizo.js` detects `file.lastModified` (~2 s watch + focus/pre-write checks), performs a 3-way shallow top-level key merge (`fields`, `lists`, `custom`), protects `document.activeElement`, and backs up any same-key collision to `↺ Restore`.
2. **Online Mode (Static Web Hosts like GitHub Pages) ↔ Save-to-PC App Exchange (`D41`):**
   - When the same `.html` file is hosted online (`https://...`), no direct server-file write is possible, yet `localStorage` persistence and 3-way merge against future server deploys work out of the box.
   - Instead of showing a misleading amber _"Click to Link Disk"_ warning, `naizo.js` enters **Online Mode**: the status pill shows **`Saved in Browser`**, `⌘S` / `Ctrl+S` flushes to browser storage with visual confirmation, and **`↺ Reset`** (with an inline Shadow DOM confirmation popover + backup) lets visitors restore the published template state.
   - At any moment, clicking **`⬇ Save to PC`** (`Naizo.downloadHTML()`) downloads the single `.html` file with the user's current `#naizodb` data, baked form attributes, and a portable CDN `<script src>` URL. When the user opens that downloaded `.html` file on their computer (`file://`), it automatically boots in **Local Mode** at the exact state they had on the web—ready for local disk sync and AI agent collaboration.
3. **Declarative Mini-API Client (`naizo-get` / `naizo-post`) — Bridging External APIs & Webhooks into `#naizodb` (`D43`, `D50`, `D51`):**
   - Elements with `naizo-get` / `naizo-post` (or `Naizo.fetch()`) pull JSON/text from HTTP endpoints into `#naizodb` (`fields`, `lists` via `Naizo.setList()`, `custom`, or full store) or push `#naizodb` payloads out to webhooks and local agent servers using CORS-safelisted `text/plain;charset=UTF-8` requests (with optional `naizo-cors="no-cors"` for blind webhooks) that work even from `file://` (`Origin: null`), while surfacing network status via the rightmost `18×18px` `#net` wired-globe indicator without altering `#dot` or `#status` (`EC36`).
   - In **Local Mode**, fetched API data is persisted directly into `<script id="naizodb">` on disk so a local CLI AI agent can immediately read and act on remote data without needing network credentials itself; in **Online Mode**, fetched data is persisted in `localStorage` (`Saved in Browser`) and included whenever the user clicks **`⬇ Save to PC`**.

## Core promises (product invariants — never compromise)

1. **In-file canonical JSON database (`#naizodb`)** — `<script id="naizodb" type="application/json">` in `<head>` holds `{ _meta, fields, lists, custom }` in clean, 2-space indented JSON that AI agents can read and edit directly on disk and Git can diff cleanly. Amended for `M4` by `D15`: keys without a matching DOM binding pass through untouched instead of being dropped on load.
2. **Two-way Human ↔ Agent conflict resolution & live watch** — On page load, before disk writes, on window focus, and via a lightweight ~2 s `file.lastModified` watch while a linked tab is visible, `naizo.js` compares the on-disk `#naizodb` block against the last known disk state. When the file on disk was modified externally (e.g., by a CLI AI agent running side-by-side), `naizo.js` performs a shallow top-level key merge (`fields[k]`, `lists[k]`, `custom[k]`), guards `document.activeElement` against mid-keystroke overwrite, and on same-key collision lets disk win while preserving the browser state in `naizodb_backup_<key>` with a 1-click `↺ Restore` action in the status pill (`D16`, `D20`, `D27`).
3. **Surgical disk sync & clean HTML serialization** — Syncing to a linked file on disk via the File System Access API (`FileSystemFileHandle` persisted in IndexedDB) rewrites only the `<script id="naizodb">` block in place, leaving all other bytes of the file untouched so third-party runtime DOM mutations (Tailwind Play CDN, Lucide, Mermaid) never bloat saved files (`D16`, `D24`). Explicit full-document export (`Naizo.exportHTML()` and fallback HTML download) bakes live input/select/checkbox/textarea values into HTML attributes on a cloned document and strips `[naizo-strip]` / `[data-naizo-strip]` elements (`#__naizodb_host__`, `#__naizodb_styles__`, injected list controls, and hosted-only scripts/overlays) while keeping user `[naizo-ignore]` elements intact (`D12`, `D23`, `D47`).
4. **Dual declarative attribute syntax + programmatic API** — Both concise `naizo` / `naizo-*` attributes (`naizo="key"`, `naizo-list="name"`, `naizo-item`, `naizo-ignore`, `naizo-strip`, `naizo-get`, `naizo-post`) and HTML5-compliant `data-naizo` / `data-naizo-*` attributes work interchangeably alongside the `window.Naizo` (`window.NaizoDB`) API (`D08`, `D38`, `D43`, `D47`).
5. **Zero runtime dependencies** — `naizo.js` ships as a standalone vanilla JavaScript IIFE (`dist/naizo.js` and minified `dist/naizo.min.js` built from `src/iife.ts`) usable directly via `<script src="./dist/naizo.js" defer></script>` or npm-backed CDN (`jsDelivr` / `unpkg`, `D34`, `D38`, `D39`), plus side-effect-free ESM and TypeScript declarations (`dist/index.mjs`, `dist/index.d.mts`) built from `src/index.ts` via Vite+ (`D06`, `D17`, `D25`, `D28`). Local development, CI, and release preparation keep the tracked readable browser bundle synchronized with `src/` (`git diff --exit-code dist/naizo.js` after `vp pack`, `D35`, `D46`).

## Design priority

Keep the tool lightweight, fast, and easy to add to ordinary HTML (`D26`, `D27`). Prefer a small API, useful defaults, and optional escape hatches. Preserve authors’ unknown JSON data and freedom to build custom widgets; require only what binding and safe persistence need. Reduce repeated DOM/serialization work before adding optimization machinery. Data-loss prevention and truthful persistence status (`Browser Cache` vs. `Saved in Browser` in Online Mode vs. `Synced to Disk` after local file write, `EC36`, `D41`) remain part of the core promise.

## Scope and non-goals

- **In scope:** Declarative scalar field binding (`input` including numeric `number`/`range`, `textarea`, `select` including `multiple`, `<details>`, plain-text `[contenteditable]`, `[naizo]`, `[data-naizo]`), single-level declarative list repeaters (`[naizo-list]` / `[data-naizo-list]` including self-bound `[naizo-item]` and `<tbody naizo-list>`), programmatic `window.Naizo` (`window.NaizoDB`) API (`get`, `set`, `delete`, `getField`, `setField`, `deleteField`, `getList`, `setList`, `addItem`, `updateItem`, `moveItem`, `removeItem`, `fetch`, `bind`, `save`, `unlink`, `reset`, `copyJSON`, `exportHTML`, `downloadHTML`) with `naizo:hydrate` / `naizo:change` / `naizo:item` / `naizo:fetch` events, `localStorage` caching, Local Mode (`⌘S` / `Ctrl+S` save/link, surgical File System Access API disk write-back with IndexedDB handle persistence, ~2 s live watch, and 3-way shallow merge), Online Mode (`naizo-mode`, `Saved in Browser`, safe `↺ Reset` with Shadow DOM confirmation + backup, and portable `⬇ Save to PC` `.html` download for web-to-local app exchange, `D41`), declarative Mini-API Client (`naizo-get`, `naizo-post`, `naizo-into`, `naizo-path`, `naizo-body`, `naizo-trigger`, `naizo-cors`, `#net` wired-globe indicator, `D43`, `D50`, `D51`), and 1-click `#naizodb` JSON clipboard copy (`Naizo.copyJSON()`).
- **Non-goals:** Backend servers, multi-user real-time network sync, general UI layout/widget directives (`naizo-tab`, `naizo-filter`, `D43`), or full frontend framework/virtual DOM replacement.
