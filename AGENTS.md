# AGENTS.md — naizo

## What this project is

**`naizo.js`** (`naizo` project, npm package `naizojs`) — zero-dependency, self-persisting HTML built-in database (`#naizodb`) and declarative list repeater (`[naizo-list]` / `[data-naizo-list]`) for Human + AI Agent workflows. Its name comes from the Japanese **_naizō_ (ないぞう)**: both **内蔵 (_built-in / embedded_)** and **内臓 (_internal organs_)**. It turns static `.html` files (dashboards, interactive studios, personal trackers, option labs, calculators, notebooks, specs, plans, checklists, triage boards, and custom micro-tools) into interactive, human-editable applications whose state syncs between the DOM, `<script id="naizodb" type="application/json">`, `localStorage`, and the local `.html` file on disk.

See [docs/PRODUCT.md](docs/PRODUCT.md) for product vision, target users, and scope boundaries.

Core promises (never compromise these):

1. **In-file canonical state (`#naizodb`) & 100% synchronous store/DOM ergonomics**: `<script id="naizodb" type="application/json">` in `<head>` holds `{ _meta, fields, lists, custom }` in human- and agent-readable JSON (`2`-space indented, with `<` escaped as `\u003c`). Unbound fields, unbound lists, and extra list-item keys (such as `id`, `estimate`, or nested sub-arrays) pass through untouched via the in-memory store and row `WeakMap` (`D15`, resolving `×` / `↑ ↓` row actions by `WeakMap` identity before DOM index and keeping multiple `[naizo-list="name"]` containers synchronized, `D59`, `EC61`). Store reads/writes and bound DOM updates stay 100% synchronous (`< 0.5 ms`, with `Naizo.get()` and `Naizo.getList()` returning `O(1)` uncloned/unfrozen read-only views; `D57`, `D59`), paired with nestable `Naizo.batch(fn, options?)` persistence/event coalescing, non-reentrant FIFO `naizo:change` queueing (`EC54`), `Naizo.ready(fn)` boot readiness (`EC57`), interactive-over-passive `naizo="key"` seeding/reset precedence (`EC56`), and single `<select>` `selectedIndex = -1` unselection on `""`/`null` (`EC55`, `D57`). Under `D16` and `D23`, `<body>` is the template and `#naizodb` is the data; form attributes are baked only on full-HTML export (`Naizo.exportHTML()`).
2. **Two-way Human ↔ AI Agent sync & Status Pill UX (`#__naizodb_host__`)**: On boot, before disk writes, on tab focus, and via a lightweight ~2 s `file.lastModified` watch while a linked tab is visible, `naizo.js` compares `#naizodb` on disk against its last known disk state. External edits on disk (e.g., by a CLI/IDE AI agent) merge cleanly across unrelated top-level keys (`fields`, `lists`, `custom`) and **per list item** via a two-tier `O(N)` 3-way list merge (Path A: unique primitive `item.id` `string | number` across additions, deletions, reorders, and live per-property edits without compulsory UUID injection `D19`; Path B: conservative aligned-prefix `0 .. base.length - 1` edits + appends for `id`-less checklists, backed by compact per-item FNV-1a hashes in `naizodb_disk_hash_<key>`, `D59`, `EC58`), reconcile `[naizo-item]` DOM nodes in place across length changes without clobbering `document.activeElement` focus/caret (`EC58`), pause disk writes if a linked disk file breaks into malformed JSON (`naizodb_raw_backup_<key>` + Red `Invalid #naizodb JSON`, auto-recovering when fixed on disk, `EC59`), and back up same-key/item collisions (as well as pre-overwrite `into="db"` fetches) to `naizodb_backup_<key>` with a 1-click `↺ Restore` (`Restore Backup`) action in the translucent frosted-glass status pill (`D16`, `D20`, `D27`, `D50`, `D59`, `D62` — clearing stale pre-link non-conflict backups on first-time `showSaveFilePicker` link alongside `6. Reset` while keeping active boot, link-time, post-link, and `Resume Disk Sync` backups intact, `EC64`). The pill renders the `20px` _Maru ni Mitsuishi_ (`丸に三つ石` / `品`) `#dot` crest with 5 narrative motion states (`Boot-Up`, `Saving Heartbeat` with `1.55s` cycle completion, `Conflict Clash`, `Needs Permission Wave Pulse`, `Error Sync Pulse`), `22×22px` circular icon buttons in strict `1..6` left-to-right order (`1. Link/Unlink Disk`, `2. Save to PC`, `3. Copy JSON / ✓ Copied`, `4. Repair JSON` Wrench on startup or live malformed `#naizodb` JSON `EC02`/`EC04`/`EC59`, `5. Restore Backup`, `6. Reset` in Online & unlinked Local Mode), the rightmost `#net` wired-globe network indicator, and FLIP 4-corner snap drag persisted in `naizodb_ui_<key>` with optional declarative initial corner hint `naizo-pill-corner` / `data-naizo-pill-corner` (`bottom-right` default across `bottom-right | bottom-left | top-right | top-left`, `<body>`-over-`<html>` precedence, user-drag priority in `naizodb_ui_<key>`, and export preservation; `D50`, `D56`, `D57`, `EC48`, `EC52`) — or can be hidden opt-in via `naizo-no-pill` / `data-naizo-no-pill` (`="false"` opts out) while keeping `#__naizodb_styles__`, `localStorage`, live disk sync, `⌘S` / `Ctrl+S`, malformed-JSON `console.warn` diagnostics, export preservation, and `Naizo.link(): Promise<boolean>` active (`D56`, `EC53`).
3. **Surgical disk sync & clean HTML export**: Writing to a linked file via the File System Access API (`showSaveFilePicker` with URL-decoded `suggestedName`, a rename-friendly wrong-file link guard on non-empty conflicting `#naizodb` files, and handle persisted in IndexedDB `NaizoDB_Handles`, `EC60`) skips `<!-- ... -->` HTML comments and preceding raw-text `<script>`/`<style>` blocks, skips `createWritable()` when the on-disk `#naizodb` block is already identical (preserving `file.lastModified` / `mtime`, `EC59`), and surgically updates only the `<script id="naizodb">` block in place so third-party runtime DOM mutations (e.g., Tailwind CDN, Lucide, Mermaid) never pollute the file on disk (`D16`, `D24`, `D59`). Full-HTML export (`Naizo.exportHTML()` and Blob download fallback) bakes form attributes on a cloned document and strips `[naizo-strip]` / `[data-naizo-strip]` elements (`#__naizodb_host__` Shadow DOM pill, `#__naizodb_styles__`, injected list controls, and hosted-only scripts/overlays) while keeping user `[naizo-ignore]` elements intact (`D12`, `D23`, `D47`).
4. **Dual attribute syntax**: Both short attributes (`naizo="key"`, `naizo-list="name"`, `naizo-item`, `naizo-template`, `naizo-ignore`, `naizo-strip`, `naizo-no-pill`, `naizo-pill-corner`, `naizo-get`, `naizo-post`, etc.) and HTML5-compliant `data-*` aliases (`data-naizo="key"`, `data-naizo-list="name"`, `data-naizo-item`, `data-naizo-template`, `data-naizo-ignore`, `data-naizo-strip`, `data-naizo-no-pill`, `data-naizo-pill-corner`, `data-naizo-get`, `data-naizo-post`, etc.) are supported everywhere (`D08`, `D43`, `D47`, `D56`, `D57`).
5. **Zero-dependency drop-in**: `naizo.js` is a standalone vanilla JavaScript IIFE (`dist/naizo.js`) with no runtime dependencies, loadable locally or via CDN (`jsDelivr` / `unpkg`), authored in TypeScript (`src/index.ts` and `src/iife.ts`) and managed with the [Vite+](https://viteplus.dev/) (`vp`) toolchain.

## Authoring HTML with `naizo.js` (AI Agent Instructions)

Whenever you generate or update an interactive HTML application (dashboards, studios, personal trackers, option labs, calculators, notebooks, plans, specs, checklists, triage boards, or custom editors), make it self-persisting using **`naizo.js`** and follow the **9 framework-free Golden Rules** (`D57`, `D58`; see [docs/USAGE.md](docs/USAGE.md), [skills/naizo/SKILL.md](skills/naizo/SKILL.md), and starter templates in `examples/starter.html`, `examples/checklist.html`, `examples/notes.html`, `examples/inventory.html`, and `examples/weather.html`):

1. **Embed `#naizodb` in `<head>` & Scope with `<html naizo-id="...">` (`D13`, `D16`, `EC11`):** Set a descriptive `<html naizo-id="project-artifact-slug">` (so `localStorage` and IndexedDB handles never collide on `localhost` or `file://`) and include `<script id="naizodb" type="application/json">` at the top of `<head>` initialized with:
   ```json
   {
     "_meta": {},
     "fields": {},
     "lists": {},
     "custom": {}
   }
   ```
2. **Load `naizo.js`:** Include `<script src="./dist/naizo.js" defer></script>` for a local copy, or use one npm-backed CDN URL: `https://cdn.jsdelivr.net/npm/naizojs@latest/dist/naizo.js` / `https://unpkg.com/naizojs@latest/dist/naizo.js`. Use `dist/naizo.min.js` for the prebuilt minified bundle. `@latest` follows npm releases as caches refresh; use an exact version such as `@0.1.0` for a fixed artifact, or `https://cdn.jsdelivr.net/gh/nickosh/naizo@main/dist/naizo.js` (or local `./dist/naizo.js`) for the latest in-development build on `main`. Prefer the npm-backed URLs when authoring release CDN examples (`D34`, `D38`, `D39`).
3. **Standalone Fields, Plain-Text Leaves (`EC19`/`EC56`), Safe `<select>` Rules (`EC15`/`EC55`), & `naizo-ignore` vs. `naizo-strip` (`D22`, `D47`):** Bind inputs (`text`, `number`, `range`, `checkbox`, `radio`), `<textarea>`, `<select>` (including `multiple`), `<details>` (`open` state), `contenteditable` blocks (plain text via `textContent`), and passive plain-text leaf elements (`<span naizo="key">`, `<h3 naizo="key">`) using `naizo="key_name"` (or `data-naizo="key_name"`). Interactive controls always take seeding and `<form>` reset precedence over passive leaves regardless of DOM order and live-mirror updates via `textContent` (`EC19`, `EC56` — never mutate `innerHTML` on a bound `naizo="key"` element). Include `<option value="">— Select… —</option>` on nullable `<select>` controls (`""`/`null` sets `selectedIndex = -1` without warning while unknown non-empty values warn and stay preserved in memory, `EC15`, `EC55`), and remember `<select>` always stores `string` values (use `<input type="checkbox">` for booleans, never raw boolean `false` on `<select>`). Use `naizo-ignore` for custom UI kept on export and `naizo-strip` for transient or hosted-only elements stripped on `Naizo.exportHTML()` / `Naizo.downloadHTML()`.
4. **Dynamic Lists (`naizo-list`), `<template naizo-template>`-First Authoring, Pass-Through Keys (`D15`), & Non-Destructive Filtering (`D43`, `D58`, `D59`):** Wrap repeating containers in `naizo-list="list_name"` (or `data-naizo-list="list_name"`, supporting multiple synchronized containers sharing the same `list_name` across `setList`/`addItem`/`updateItem`/`removeItem`/`moveItem`/DOM edits, `EC61`). Prefer authoring a single `<template naizo-template>` blueprint with `0` duplicated static `[naizo-item]` shells in `<body>` while `<script id="naizodb">` holds canonical initial items (`D16`, `EC09`). Inside `[naizo-item]` (or `data-naizo-item`), wrap `<label>` elements directly around inputs instead of duplicate `id`/`for` pairs (`EC39`). Unbound item keys (`id`, `estimate`, URLs, sub-arrays) pass through automatically via `WeakMap` row bindings without `.sr-only` dummy bindings (and `[naizo-remove]` / `[naizo-move]` resolve row indices via `WeakMap` identity before DOM index, `EC61`); including unique primitive `id` (`string | number`, never auto-stamped, `D19`) on multi-field card/row items unlocks `O(N)` item-by-item 3-way merge across additions, deletions, reorders, and per-property live edits (`EC58`) — render rich HTML (`<a>`, Markdown, badges, memoized `dataset.slotSignature` sub-arrays) into `[naizo-ignore]` containers directly from `Naizo.getList()` (`D15`, `EC14`). Never filter `[naizo-item]` rows by removing them from the DOM (toggle `row.hidden = !matches`), and use `Naizo.setList(name, items)` for single-pass bulk replacement or clearing (`[]`).
5. **Custom Widgets, Fast Read-Only Views, Batching, Boot Lifecycle, Status Pill Placement, & Mini-API Client (`window.Naizo`, `Naizo.batch`, `Naizo.ready`, `naizo-pill-corner`, `naizo-no-pill`, `naizo-get`, `naizo-post`):** Persist custom JavaScript state via `Naizo.get('key')`, `Naizo.set('key', value)`, and `Naizo.delete('key')`; manipulate fields, lists, batches, readiness, and HTTP endpoints programmatically via `Naizo.getField`, `Naizo.setField`, `Naizo.deleteField`, `Naizo.getList`, `Naizo.setList`, `Naizo.addItem`, `Naizo.updateItem`, `Naizo.moveItem`, `Naizo.removeItem`, `Naizo.batch(fn, options?)`, `Naizo.ready(fn)`, `await Naizo.fetch(url, options?)`, `Naizo.bind(root)` (skipping persistence when seeding causes zero store changes, `EC59`), `await Naizo.save()`, `Naizo.reset()`, `await Naizo.link()`, `await Naizo.unlink()`, `await Naizo.copyJSON()`, `Naizo.exportHTML()`, and `Naizo.downloadHTML(filename?)`; or pull/push HTTP payloads declaratively with `naizo-get` / `naizo-post`, `naizo-into` (`field:`, `list:`, `custom:`, `db` with automatic pre-overwrite `naizodb_backup_<key>` backup `EC59`, or DOM-only `#selector`), `naizo-path`, `naizo-body`, `naizo-trigger="click|init|load"`, and `naizo-cors="no-cors"` (surfacing the rightmost `#net` wired-globe indicator, `D43`, `D50`, `D51`, `D52`). Treat `Naizo.get()` and `Naizo.getList()` return values as fast `O(1)` uncloned/unfrozen read-only views for `< 0.5 ms` 60fps reads — never mutate returned objects or arrays directly in place; always mutate via `Naizo.set*`, `updateItem`, `addItem`, `setList`, or `batch` (`D59`). Never register `naizo:hydrate` inside `DOMContentLoaded` when loading `<script defer>` — attach `'naizo:hydrate'`, `'naizo:change'`, `'naizo:item'`, and `'naizo:fetch'` listeners at top level or call `Naizo.ready((db) => ...)` (`EC57`, keeping `[naizo-ignore]` item enhancements idempotent and matching static `hidden` attributes to initial `#naizodb` defaults). Use `Naizo.batch(fn, options?)` for multi-item/cross-scope updates (`{ silent: true }` for silent derived writes, `{ deferPersist: true }` for 60fps range/canvas scrubs; `EC54`), memoize custom `[naizo-ignore]` subtrees (`dataset.slotSignature` or `e.detail` checks across `{ index, action, source: 'dom' | 'api' }`), and attach delegated native `'change'` listeners (never `naizo:change`, which fires on `input`) for one-time `name → slug` derivations (`D57`). Place app toasts at `top-right` or `bottom-center`, or set `naizo-pill-corner="bottom-left"` (`naizo-pill-corner` / `data-naizo-pill-corner` on `<body>` or `<html>`) when `bottom-right` hosts fixed app controls (`D50`, `D57`). Only add `naizo-no-pill` / `data-naizo-no-pill` when the user asks to hide the Status Pill or build custom persistence UI, and when doing so in Local Mode, surface `⌘S` / `Ctrl+S` or an `await Naizo.link()` button so users can still persist data to `<script id="naizodb">` on disk (`D56`, `EC53`).
6. **Reading, Updating, & Testing Files on Disk, Browser Matrix, & Dev-Server Rules (`D16`, `D59`, `EC46`, `EC58`–`EC61`):** When inspecting or modifying an existing HTML file on disk, treat `<body>` as the template and `<script id="naizodb">` as the canonical data (`D16`): read or edit `<script id="naizodb">` to change data (skipping `<!-- ... -->` HTML comments when scanning raw HTML, `EC60`), and edit `<body>` markup to change the view. `naizo.js` automatically hydrates the DOM, merges external disk edits across unrelated top-level keys (`fields`, `lists`, `custom`) and per list item (Path A unique `item.id` + Path B conservative aligned-prefix `0 .. base.length - 1` + appends for `id`-less checklists, falling back to `naizodb_backup_<key>` + `↺ Restore` on shifts/deletions/collisions) via compact FNV-1a hashes (`naizodb_disk_hash_<key>`), reconciles `[naizo-item]` DOM nodes in place across length changes while preserving `document.activeElement` focus/caret (`EC58`), pauses writes with Red `Invalid #naizodb JSON` + `naizodb_raw_backup_<key>` + `4. Repair JSON` if disk JSON breaks mid-session (auto-recovering when fixed on disk, `EC59`), skips no-op disk writes to preserve `mtime` (`EC59`), and guards against linking an unrelated non-empty `#naizodb` file via `window.confirm()` while keeping disk renames, empty `"Save As"` files, and renamed copies of the same app unprompted (`EC60`). Live two-way disk sync works out of the box in **Chrome, Edge, Arc, and Opera** (the initial OS Save dialog asks _"Replace?"_ once to confirm in-place write permission), requires enabling `brave://flags/#file-system-access-api` once in **Brave**, and falls back cleanly in **Safari & Firefox** (`localStorage` + `.html` download + `📋 Copy JSON`). Never open disk-linked files through file-watching live-reload dev servers (**Vite**, **VS Code Live Server**, **BrowserSync** — every surgical `#naizodb` save triggers a full page reload loop); open via `file://` or a plain non-watching static server (`python3 -m http.server`, `npx serve`). When testing fresh disk edits on an unlinked `localStorage` page, use `↺ Reset` / `Naizo.reset()` so cached browser keys do not mask unchanged keys.
7. **Visual Design & Styling (`D45` — Author Preferences First, Minimalist Editorial Fallback, & Clean `"theme": "system"`):** Always follow the user's or author's explicit visual, layout, or CSS framework preferences first. Only when the author has not specified any styling preferences, default to calm, human-readable **Washi Editorial** minimalism (`#faf8f5` warm paper in light mode / `#141311` in dark mode, `1.65–1.75` body line-height, hair-thin `1px` rules instead of nested drop-shadow bento cards or badge clutter, spaced en-dashes `–` instead of unspaced em-dashes, balanced 3-column tables without `white-space: nowrap` on long keys, and `"theme": "system"` with CSS `@media (prefers-color-scheme: dark)` so initial page load never calls `Naizo.setField()` or mutates `store` on boot, `EC48`).

[`pnpm-workspace.yaml`](pnpm-workspace.yaml) sets `runtimeOnFail: ignore` and `pmOnFail: ignore` so VP owns environment selection, and `lockfile.includeResolutionSettings: true` so the lockfile records resolution policy for consistent frozen installs. Keep dependency build approvals explicit if future dependencies need lifecycle scripts.

- `vp install` — install dependencies
- `vp check` — format (`Oxfmt`), lint (`Oxlint`), and type-check (`tsgolint`) in one pass
- `vp test` — run Vitest suite (`tests/**/*.test.ts`) after `vp pack`, because tests load generated browser output
- `vp pack` — build library outputs (`dist/naizo.js`, `dist/naizo.min.js`, `dist/index.mjs`, `dist/index.d.mts`) via `tsdown`
- `vp dev` — start local playground server (`http://localhost:3000`, serving `site/index.html`)

Use proportional verification:

- Documentation edits require link/reference review and whitespace checks (`git diff --check`).
- Code or behavior changes in `src/`, `dist/naizo.js`, `site/index.html`, or `examples/` require `vp check`, `vp test`, and `vp pack` (when `vite-plus` is installed), syntax checks (`node --check dist/naizo.js`), `git diff --exit-code dist/naizo.js` after `vp pack`, and JSON validation of `package.json` and embedded `#naizodb` blocks. Run `vp pack` before `vp test` and before using the local demo, and always commit the freshly packed `dist/naizo.js` whenever `src/` changes: both `ci.yml` and `release.yml` enforce `git diff --exit-code dist/naizo.js` (`D46`) so local `./dist/naizo.js` and `https://cdn.jsdelivr.net/gh/nickosh/naizo@main/dist/naizo.js` always match `src/` on `main`. Explicit release preparation also builds `dist/naizo.js` in a read-only job and includes it in the Release Please PR (`D35`). The bot-created release PR receives no CI run; the preparation job's build/test verifies its bundle, and tagged publication enforces tracked-bundle freshness. Ordinary CI tests freshly built outputs, verifies `dist/naizo.js` freshness and `_site/` staging, and deploys GitHub Pages only on release merges (`chore(main): release `) or manual `workflow_dispatch` on `main` (`pages_source: 'main' | 'latest-release'`, defaulting to `'main'` with `'latest-release'` building from the latest published `vX.Y.Z` release tag; `D37`, `D46`, `D48`, `D49`). Only the readable bundle is tracked.
- Rerun checks when changes or unresolved concerns justify it, not only at closeout. Do not claim unrun checks passed or treat plans/fixtures as proof of passing behavior.

## Git workflow

- After completing and verifying each coherent change, including documentation changes, reconcile project memory and create a local commit without asking again unless the user explicitly requests otherwise.
- Milestones in `docs/PLAN.md` (`M10`, `M11`, `M12`, ...) are numbered for stable reference rather than strict sequential order (`D55`): follow the active priority queue in `Current state and next action`, respect owner-deferred milestones, check each milestone's **`Prerequisites:`** note before starting, and keep `main` green and releasable after every completed substep (`D44`, `D46`, `D55`).
- When an active milestone or task in `docs/PLAN.md` has substeps (e.g., `M5.1` and `M5.2`, or `M4.5a`–`M4.5e`), complete, verify, reconcile project memory, and create a separate local commit for **each substep in sequence** before starting the next substep — never batch multiple planned substeps into a single commit (`D02`, `D44`).
- Use Conventional Commits for commit messages (`type(scope): subject`); include a scope only when it adds clarity. Common types: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci`, and `build`.
- Every commit must include a factual body after the subject and a blank line explaining what changed, why, and any relevant limitations. Do not create subject-only commits. Scale the detail to the change. Validation results and checks not run belong in closeout documentation and chat; they are not required in commit bodies.
- Do not add a `Co-authored-by: Copilot` trailer (or any other AI co-author trailer) to commit messages.
- Stage only changes belonging to the completed work. Preserve unrelated staged and unstaged changes. Leave incomplete or verification-blocked work uncommitted and report the blocker unless the user requests a checkpoint.
- This authorizes local commits only. Push, tag, publish, or open a pull request only when separately requested by the user.
